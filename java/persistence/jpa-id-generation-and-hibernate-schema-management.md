# JPA ID Generation and Hibernate Schema Management

Two related JPA and Hibernate settings answer different questions:

- `@GeneratedValue(strategy = GenerationType.IDENTITY)` controls how a new entity's primary key is generated.
- `spring.jpa.hibernate.ddl-auto` controls what Hibernate does with the database schema when the application starts.

An entity may use `IDENTITY` regardless of whether Hibernate creates, validates, updates, or leaves the schema alone. In production, schema changes are usually managed separately with a migration tool such as Flyway or Liquibase.

## Generating an ID with `IDENTITY`

`@GeneratedValue(strategy = GenerationType.IDENTITY)` tells JPA to use a database identity column to generate an entity's primary-key value when a new row is inserted.

```java
@Entity
@Table(name = "customers")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    public Long getId() {
        return id;
    }

    public void setName(String name) {
        this.name = name;
    }
}
```

These annotations come from `jakarta.persistence`. `@Table(name = "customers")` explicitly selects the table name; JPA does not automatically pluralize entity names. The class has an implicit public no-argument constructor, and its field annotations select field access, so JPA does not require getters and setters for every persistent field.

When you create and save a new customer, you do not set the ID yourself. Assume `customerRepository` is a Spring Data JPA repository for `Customer` with an ID type of `Long`:

```java
Customer customer = new Customer();
customer.setName("Alice");

customerRepository.save(customer);
```

The database generates the ID, typically using an auto-incrementing or identity column:

```text
id | name
---+------
1  | Alice
2  | Bob
```

After the insert, JPA generally makes the generated value available on the entity:

```java
System.out.println(customer.getId()); // e.g. 1
```

The generated schema may resemble:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(255)
);
```

Exact SQL depends on the database and Hibernate configuration. `Long` is commonly used because the generated numeric value can be `null` before the entity is persisted.

## Managing the Schema with `ddl-auto`

Set Hibernate's schema-management behavior with Spring Boot's `spring.jpa.hibernate.ddl-auto` property:

```properties
spring.jpa.hibernate.ddl-auto=validate
```

The available values are:

| Value | What it does |
| --- | --- |
| `none` | Disables Hibernate schema management. Hibernate does not create or validate the schema; tables must already exist or be created by another mechanism, such as Flyway, Liquibase, or SQL scripts. |
| `validate` | Does not modify the schema. Compares entity mappings with the existing database and fails at startup when it finds a mismatch, such as a missing table or column or an incompatible type. Useful as a safety check. |
| `update` | Compares mappings with the existing schema and issues statements to bring it closer to the mappings. It does not drop existing tables or columns, but it is not a substitute for reviewed migrations and can be risky on shared or production databases. |
| `create` | Drops and recreates the schema from the entity mappings at startup. Existing data is lost. |
| `create-drop` | Creates the schema at startup and drops it when the Hibernate `SessionFactory` shuts down. Useful for short-lived test databases. |

## Spring Boot Defaults

If `spring.jpa.hibernate.ddl-auto` is not set, Spring Boot chooses a default based on the database and whether a schema manager is present:

- An embedded database such as H2, HSQLDB, or Derby, with no Flyway or Liquibase detected: `create-drop`.
- Other cases, including external databases such as PostgreSQL or MySQL, or a detected schema manager: `none`.

This means switching from an in-memory database to a real database can change the default behavior. As the [Spring Boot documentation](https://docs.spring.io/spring-boot/reference/data/sql.html) warns:

> Be careful when switching from in-memory to a "real" database that you do not make assumptions about the existence of the tables and data in the new platform. You either have to set ddl-auto explicitly or use one of the other mechanisms to initialize the database.

For predictable deployments, set the property explicitly and decide which tool owns schema creation and updates.

## Hibernate Property and Startup Scripts

The native Hibernate property is `hibernate.hbm2ddl.auto`. In Spring Boot, you can set it directly through Hibernate's property namespace instead:

```properties
spring.jpa.properties.hibernate.hbm2ddl.auto=validate
```

Usually, prefer the Spring Boot property `spring.jpa.hibernate.ddl-auto` for this setting.

An `import.sql` file at the classpath root runs at startup only when Hibernate creates the schema with `create` or `create-drop`. To run Spring Boot's `data.sql` initialization after Hibernate has created the schema, set:

```properties
spring.jpa.defer-datasource-initialization=true
```

To inspect SQL statements, enable the `org.hibernate.SQL` logger. Hibernate's schema-tool debug logging can also help diagnose schema creation and validation.

## Practical Choices

- Local development with H2: use `update` for a persistent local schema, or rely on the `create-drop` default for a disposable one.
- Tests: `create-drop` gives a fresh schema for each application or test-context lifecycle.
- Production or shared databases: use `none` or `validate`; avoid `update` and `create`. Prefer Flyway or Liquibase to apply reviewed, versioned schema migrations.

## Quick Distinction

- `@Id` marks a field as the primary key.
- `@GeneratedValue` says the primary-key value is generated automatically.
- `GenerationType.IDENTITY` says the database identity column generates that value.
- `spring.jpa.hibernate.ddl-auto` controls Hibernate's schema actions; it does not choose the entity's ID-generation strategy.
